## 2. 【第一批次重点】Thread —— 顶栏 + 排序 + 属性页

### 2.1 信息架构（**已按用户 5 修订**）

Thread 模块 = **多个并列界面**，不是一页折叠区：

```
Thread 模块
├── ① 事件流（主界面）— 只放"可正常排序"的事件
├── ② 已归档 — 已完成 + 时间不足（"不可能完成"）+ 已逾期   【用户 5 + 11】
└── 属性页 = 覆盖在①之上的弹出层（不是独立 tab）
```

> ⚠️ **请扫一眼**：【用户 5】说"已完成或者时间不足我们单独放在另一个界面"，我据此把**已完成 / 时间不足 / 已逾期**合并成一个「已归档」界面（内部分三组）。若你想拆成两个界面，说一声我拆。

主界面自上而下：

```
┌─ Thread ──────────────────────────────────────────┐
│ [顶栏]  [🎯 期末数学▾] [🔋7]      [⚙] [🔄 更新与排序]│
├───────────────────────────────────────────────────┤
│ 排序结果（仅点〔🔄〕后生成；否则提示"需要重新排序"）│
│  ○ 任务标题          需30min · 🔋6 · [作文]        │
│  ○ ...                                            │
└───────────────────────────────────────────────────┘
```

每条自身**只有**：完成圆点、标题、时长、精力要求、标签末级、（可选）提醒图标。**没有理由文案、没有分数**（P6）。

### 2.2 顶栏（**已按用户 2、3、8、10 修订**）

### 2.3 排序与"黄/红"标注（**已按用户 16 修订，语义改动最大**）

**核心语义**：`expected_time` 与 `deadline` **相互独立、互不影响**；两者都只是"结果观测点"。

| 标注 | 触发条件（**只看 deadline**） | 处理 |
| --- | --- | --- |
| 🔴「不可能完成」 | `estimate_minutes > (deadline − now) − 区间内忙碌块总时长` | 移出主列表 → 「已归档 · 时间不足」 |
| 🔴「已逾期」 **【用户 11】** | `deadline < now` | 单独一类，也进「已归档」，**文案与时间不足区分** |
| 🟡「期望时刻临近」 **【用户 16】** | 有 `expected_at` 且已临近/已过，但**无** deadline 硬冲突 | **留在主列表**，标黄 + **提升其优先级参数** |

- 硬约束**绝不因 `expected_at` 触发**（用户明确：后者可以推迟）。
- 黄色提权实现：`ThreadRanker` 输出 `expectedPressure` 分量（0..1），在总分里作为**可调权重**加入（默认小权重，值在属性页可见可改）。
- 【用户 16】移动事件时刻（Time 冲突一键调整）：**只挪 `expected_at`，不动 `deadline`**；挪完仍不够，**只提示**，不自动改。

### 2.4 可解释性与「属性」页（**已按用户 6、13 修订**）

**列表不解释、属性页全解释**：

- 每个事件一个 `⚙` icon → 打开「属性」页（手机全屏页 / 桌面侧栏或对话框）。
- 属性页内容（**全部可编辑**，每个参数卡底部一行小字解释现实意义）：
  - 标题、备注
  - `estimated_duration`（期望用时）+ 小字："你估计要花多久；排序用它判断 deadline 是否装得下"
  - `expected_time`（期望时刻）+ 小字："你打算什么时候做；临近时它会变黄并提权，但不会变成红色错误"
  - `deadline`（截止时刻）+ 小字："真正的硬底线；装不下就会进'时间不足'"
  - `energy_required`（精力要求 1–10）
  - 标签（树形，末级显示 + 点击展开完整路径）
  - **算法参数区**：该事件参与排序时**各分量原始值**（紧急度 / 目标匹配 / 状态适配 / 疲劳惩罚 / 期望压力）与**权重**，权重可改。
  - 实际用时记录（见 §2.6）

> ⚠️ **【用户 6】要求"所有参数公开、在属性里能编辑"——我理解为：权重（0.4/0.3/0.2/−0.1 等）也可被用户在属性页覆盖。** 覆盖是"该事件级"还是"全局级"？我的猜测：**属性页改的是全局权重**（改一处影响所有事件），事件级只读展示它的分量值。若你要事件级权重覆盖，那是一张新表。（Q2.4）

### 2.5 目标匹配（**已按用户 7 简化**）

只用**简单的自由文本关键词命中**：

- 词库 = 当前目标文本；对每个事件，统计目标词命中该事件标签路径的比例。
- 已确认代码 `ThreadRanker._goalMatch` 当前就是"`goal.path` 非空走路径匹配，否则走文本分词命中"——按【用户 7 + 9】，**节点路径分支不再使用**（Mindnet 已并入标签），保留代码不删但永远走文本分支。

### 2.6 实际用时（**已按用户 14 修订**）

- **不跑计时器**。完成时计算：`actual = 完成时刻 − 开始时刻`。
- 新增 `Tasks.started_at`（开始时刻；用户点"开始"时写）。
- 完成动作写：`CompletionLogs.actual_minutes`（取整到分钟）+ `include_in_model`（是否允许回喂模型）。
- **异常保护**（防"忘关"污染模型）：
  - 每条完成记录都能**单独切换**"是否作为参考"（`include_in_model`）。
  - 默认规则：`actual > estimate × 3` 且 `actual > 30min` → **默认不计入**，记录上标注"疑似中断，未计入"（用户可手动打开）。
  - **全局开关**（设置页）："用实际用时更新模型评价"总开关。

### 2.7 排序结果的生命周期（**已按用户 12 修订**）

## 4. Knowledge

### 4.1 抽卡粒度与错题重做（**已按用户 17 修订**）

- **一次一个空**（固定 1 空）【用户 17】。
- 复习效果靠**对同一则材料反复用不同挖空**达成（这正是自由挖空的设计目的）。
- 答错 → **原题重做**：把**当时那个挖空方式**打上 `active` 标记【用户 17】。
- **"立即"的含义**：**隔几张卡之后再出现**；队列没有更多卡了就**反复出现**；**必须在当天任务内出现**。
  - 实现：`active` 单元进"当日待清队列"，抽卡时优先在间隔 N 张后插入（N 见 Q4.1）；队列空了立刻再来。
